# GitHub Round-Trip Workflow

The MakeCode Arcade web editor at https://arcade.makecode.com/ uses GitHub as its sync channel. Local edits (from Claude Code) and editor edits (from the user) both flow through commits.

Sources: https://arcade.makecode.com/github/getting-started, https://makecode.com/extensions/github-authoring

## How the web editor's GitHub button works

The web editor performs commit + pull + merge + push **atomically** when the user clicks the GitHub button. From the docs:

> *"There's really no distinguishing between a commit, push, and pull — it all happens at once in the sync operation."*

This has two implications for the local side:

1. The user may push changes at any time, including while Claude Code is mid-edit.
2. Conflicts that auto-merge succeed silently; conflicts that fail land as a **pull request on GitHub** that the user must resolve manually.

## Locking the project to JavaScript-only (prevent Blocks-tab clobber)

By default the web editor shows a **Blocks** tab alongside JavaScript. For a project authored locally in TypeScript this tab is a hazard, not a feature: clicking it triggers a TS→Blocks conversion that can silently rewrite your `main.ts` (see `pitfalls.md` on namespace-shadow renames). The robust fix is to remove the tab entirely via two `pxt.json` fields:

```json
{
    "preferredEditor": "tsprj",
    "languageRestriction": "javascript-only"
}
```

- `"languageRestriction": "javascript-only"` — the editor **removes the Blocks tab**, so it can't be clicked. This is the primary guard.
- `"preferredEditor": "tsprj"` — makes `main.ts` (not `main.blocks`) authoritative on load.

Also **remove `main.blocks` from `files[]`**. The file may remain on disk; the editor ignores it when it isn't listed. Do not re-add it.

This survives the GitHub round-trip in practice — a web-editor save preserves both fields (it may bump `targetVersions.target`, which is harmless). If the Blocks tab ever reappears, `languageRestriction` was stripped: restore it, set `preferredEditor` back to `tsprj`, drop `main.blocks` from `files[]`, and re-push. **Never click the Blocks tab to "check" something** — peeking can mutate in-memory TS that then gets committed.

Symptom of an accidental revert to Blocks mode: a web-editor commit titled `Update main.blocks, main.ts` that deletes recent TS-only additions.

## Required local protocol

### Before any edit session

```bash
git pull --rebase
```

This pulls anything the user pushed from the web editor. Skipping this guarantees future merge pain.

If `pxt.json` `dependencies` changed in the pulled commits:

```bash
mkc install
```

### During edits

Work on `main.ts` and other `.ts` files. Touching `*.g.ts` or the base64 inside `*.g.jres` is forbidden — both are autogenerated and will conflict on every web-editor save.

### Before committing

```bash
mkc build -j           # must exit 0
```

A passing build means the project will also load in the web editor.

### Committing and pushing

```bash
git add .
git commit -m "<topical message describing the change>"
git push
```

Commit messages should be **topical and short** — the user will see them in the web editor's diff view. Prefer "Add coin pickup sound" over "Update main.ts".

## What the web editor commits on first push

When the user first runs "Create new repository" from the editor, it commits:
- `pxt.json`, `main.ts`, `README.md`, `.gitignore`
- `_locales/` (i18n stubs)
- A `.github/workflows/makecode.yml` auto-generated CI workflow (builds and deploys to GitHub Pages)
- A `_config.yml` for GitHub Pages
- An `assets.json` if any assets exist

The repo becomes a playable build at `https://<user>.github.io/<repo>/` if Pages is enabled.

## Conflict handling

Auto-merge usually succeeds for edits in disjoint files. If it fails, the web editor takes this path (verbatim):

> *"If the automatic merge fails, MakeCode will create a new branch, push the commit there, and then create a pull request (PR) on GitHub… Before you resolve conflicts and merge the PR, the master branch will not have your changes."*

So when conflicts happen, the user gets a PR on the GitHub repo and has to resolve it. The local clone is unaffected until the PR merges back to `master`.

### Mitigations

- Always `git pull --rebase` before letting Claude edit.
- Keep commits small and topical.
- Never edit `*.g.ts` (regenerated every web-editor save).
- Never commit `pxt_modules/` or `built/`.
- Coordinate: when the user is actively editing in https://arcade.makecode.com/, hold off on local commits. When Claude is mid-session, ask the user to refrain from pushing.

## Importing an existing game

### From a GitHub repo

```bash
git clone https://github.com/<user>/<repo>.git
cd <repo>
mkc install
mkc build -j
mkc serve              # http://127.0.0.1:7001
```

If the repo has `pxt.json` at root, this just works.

### From a share link / share ID

Share IDs look like `_AbCdEf12345` and full share URLs like `https://arcade.makecode.com/S12345-...`.

```bash
mkdir <name> && cd <name>
mkc init arcade --id <SHARE_ID_OR_URL>
mkc install
mkc build -j
```

After import, `git init && git add . && git commit -m "Initial import"` and push to a new GitHub repo. Then on the web editor side, import via "Import" → "GitHub URL".

### From a `.mkcd` / `.png` download

The web editor's "Download" button produces a PNG with the project embedded as metadata. There is no clean `mkc import file.png` command. Round-trip path:

1. Open https://arcade.makecode.com/.
2. Drag the file onto the editor.
3. Click GitHub button → "Create new repository".
4. `git clone` locally.

## Branches

URLs like `https://github.com/<user>/<repo>#mybranch` can be used as Import URLs in the web editor to pull a non-master branch. The MakeCode docs note this hasn't been heavily tested — works for casual use, expect rough edges for complex flows.

## Releases / version bumps

When pushing from the web editor, the user can opt to bump the version, which creates a tagged release. From the local side:

```bash
mkc bump --patch        # or --minor, --major
```

For a *game* project, releases mostly matter because the GitHub Pages playable build is keyed off the latest release.

## Sanity check before declaring sync done

After a push, ask the user to open the project in https://arcade.makecode.com/ via the GitHub menu. If it loads and the simulator runs, sync worked. If the editor shows compile errors that `mkc build -j` did not, the most likely cause is a `targetWebsite` mismatch in `mkc.json` (local pinned to a different beta).

## Anti-patterns

- ❌ Forcing a push that overwrites web-editor commits (`git push --force`). The user loses asset edits.
- ❌ Editing `*.g.ts` to "fix" an asset reference. Edit the asset in the web editor, then pull.
- ❌ Committing `pxt_modules/`. Different versions appear on different machines; always-stale conflicts.
- ❌ Long-running local branches diverging from `master`. The web editor only tracks `master` by default.
