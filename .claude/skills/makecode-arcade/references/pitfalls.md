# Common Pitfalls

Numbered catalog of things that look like valid TypeScript but break in Static TypeScript (STS), MakeCode Arcade's compiler. Read once at the start of any session.

## Language-level pitfalls

1. **`Promise` / `async` / `await` are banned in user code.** Use `pause(ms)`, `pauseUntil(cond)`, or `control.runInParallel(handler)` instead. MakeCode supports pseudo-async calls that look synchronous; you call blocking APIs like `game.askForString` directly without `await`.

2. **`Map<K,V>` and `Set<T>` are not implemented.** Use `{ [k: string]: V }` for string-keyed dicts. For numeric-keyed sets or anything else, use an array and `indexOf`.

3. **`for...in` is banned.** Use `for...of` for arrays, or index loops (`for (let i = 0; i < arr.length; i++)`).

4. **`var` is banned.** Only `let` and `const`.

5. **`import` and `export` at file scope are banned.** STS uses `namespace` blocks for modularity:
   ```typescript
   namespace gameLogic {
       export function scoreFor(coins: number): number { return coins * 10 }
   }
   // Call site: gameLogic.scoreFor(5)
   ```

6. **Spread/rest at call sites is unreliable.** Do not write `Math.max(...arr)`. Iterate explicitly or pass fixed-arity args.

7. **Custom tagged templates are banned.** Only these eight tags are recognized: `` img`...` ``, `` tilemap`...` ``, `` hex`...` ``, `` assets.image`...` ``, `` assets.tile`...` ``, `` assets.tilemap`...` ``, `` assets.animation`...` ``, `` assets.song`...` ``. Anything else is a compile error.

8. **Regex is not supported.** No `.match`, no `.replace(regex, …)`, no `.matchAll`. Write explicit character loops.

9. **Function overloading is banned.** Use union types or distinct names.

10. **Class instances cannot get ad-hoc fields.** `(myEnemy as any).extra = 7` is banned at runtime — classes are not extensible. Add the field to the class declaration.

11. **`Object.keys(classInstance)` does not work.** It works only on `{}` literals.

12. **`interface` with the same name as a class** is banned (nominal typing).

13. **Casts of non-class to class** are banned. Cannot cast `{}` to a class instance.

14. **`this` outside a class method** is banned.

15. **Arrays of typed ints (`uint8[]`, `int16[]`, etc.) are banned.** Use `Buffer` for byte arrays, or a regular `number[]`.

16. **`for (let i …)` closures**: each iteration gets its own `i` binding (ES6 semantics). If a closure ever needs to "freeze" the index for any reason, copy to `const idx = i` inside the loop body — but in pure STS this is rare.

17. **`function` declarations and outer-scope variables**: a `function` cannot be called before all `let`s/`const`s it captures from outer scope are defined. Verbatim from MakeCode docs: *"Identifiers defined with `function` can only be used after all variables from outer scopes have been defined."*

## File / project pitfalls

18. **Forgetting to add a new `.ts` file to `pxt.json` `files[]`** — the file is silently ignored. Always update `files[]` when creating new source files.

19. **Forgetting to run `mkc install` after editing `pxt.json` `dependencies`** — local TypeScript will show "Cannot find name X" until extension stubs land in `pxt_modules/`. (The web editor fixes itself on next load.)

20. **Committing `pxt_modules/` or `built/`** — bloat plus merge conflicts. Both must be in `.gitignore`.

21. **Editing `*.g.ts` files** — autogenerated from `*.g.jres`. Any hand-edit is clobbered the next time the asset editor regenerates them, which is every time the user saves in the web editor.

22. **Editing the base64 inside `*.g.jres`** — almost always wrong. Round-trip through the web editor for asset changes.

## CLI pitfalls

23. **Installing the wrong package.** `npm install -g mkc` installs a different, unrelated npm package. The correct command is `npm install -g makecode`. The binary works as both `makecode` and `mkc`.

24. **Mixing the legacy `pxt` CLI with `mkc`.** The `pxt` CLI is for editor target development, not games. Use `mkc` exclusively for game projects.

## Runtime / API pitfalls

25. **`SpriteKind.create()` called multiple times for the same logical kind** returns a fresh int each call. Declare each kind exactly once in a single `namespace SpriteKind { export const X = SpriteKind.create() }` block, then reference `SpriteKind.X` everywhere else.

26. **`forever()` vs `game.onUpdate()`**: `forever` runs the handler, awaits return, repeats — independently of frame rate. `game.onUpdate` runs inline in the scene loop each frame. For predictable per-frame logic use `game.onUpdate`; for periodic background work use `forever` or `game.onUpdateInterval(ms, …)`.

27. **`game.over()` vs `game.gameOver(boolean)`.** The latter is current: `game.gameOver(true)` shows the win screen, `game.gameOver(false)` shows lose. `game.over()` exists but is the older form.

28. **`tiles.setTilemap` vs `tiles.setCurrentTilemap`** — both work; `setCurrentTilemap` is the canonical name. Pick one and stay consistent within a project.

29. **`stopAnimation` leaves the last frame visible.** If you want the sprite to reset to a default pose, call `sprite.setImage(defaultImg)` after stopping.

30. **No save system in the web simulator.** Persist run-state in top-level `namespace`-scoped variables; data survives `pushScene`/`popScene` because handlers are scene-bound but module-scope data is not. Hardware-only `settings` extension is out of scope for web-sim work.

31. **Don't shadow a MakeCode namespace with a parameter/variable name.** MakeCode has top-level namespaces like `player` (multiplayer), `controller`, `game`, `info`, `scene`, `music`, `sprites`, `tiles`, `effects`, `control`. Naming a callback parameter after one — e.g. `sprites.onOverlap(SpriteKind.Player, SpriteKind.Enemy, (player, enemy) => …)` — compiles fine in `tsprj` mode, but if anyone ever clicks the **Blocks** tab the TS→Blocks converter auto-renames it (`player` → `player2`) to dodge the clash, and the rename is **incomplete**: it doesn't reach into nested arrow bodies (e.g. inside `control.runInParallel(() => …)`), so references there resolve back to the namespace and produce `Cannot use namespace 'player' as a value`. Use a non-namespace name like `playerSprite`. (`enemy`/`projectile` happen to be safe — no namespace by that name.) Locking the project to JavaScript-only removes the Blocks tab and this hazard with it — see `github-workflow.md`.

32. **`SpriteFlag.AutoDestroy` is camera-relative, not world-relative.** It destroys a sprite when it leaves the **camera viewport**, not when it leaves the tilemap world. Consequence: a sprite *spawned* off-camera (e.g. an enemy placed at `player.x + 120..200` to drift into view) is destroyed on the very next frame, before the user ever sees it — the spawner appears to fire but the count stays 0. For off-screen spawns, don't use `AutoDestroy`; run a manual cleanup sweep in `game.onUpdate` that despawns by world position instead.

33. **Sprites are clamped at tilemap world walls.** Tilemap scenes hard-collide sprites at world bounds (`x = 0`, `x = tilemap.width * 16`, similarly for `y`). A sprite moving toward an edge stops dead at the wall and piles up there. This breaks player-relative cleanup: `if (e.x < player.x - 100)` never fires when the player is at the left edge (the threshold goes negative but enemies clamp at `x ≈ 6`). Combine a relative threshold **and** an absolute world-edge threshold (e.g. `e.x < 16`) so wall-stuck sprites actually get removed.

## Self-check before declaring a change done

Run this fast grep on any changed `.ts` file:

```bash
grep -nE 'import |export |async |await |Promise|new Map|new Set|for *\(.*\bin\b|^var |\.match\(|\.replace\(/' main.ts
```

Any hit is a likely STS violation. Investigate and fix.
